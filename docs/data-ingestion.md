# Orchidarium data ingestion plan

## When do orchids get loaded?

Demo records can be loaded immediately with `supabase/seed.sql` after the initial migration. Real production data should be loaded only after source-specific permission, license, and attribution rules are confirmed.

## Recommended load order

1. `sources`: POWO/WCVP, GBIF, RHS/IOR, award bodies, nursery/import evidence.
2. `genera`: canonical genus names and standard horticultural abbreviations.
3. `species`: accepted Orchidaceae taxa from WCVP/POWO, enriched with GBIF taxon keys where permitted.
4. `species_synonyms`: synonyms and historical names mapped to accepted species.
5. `grexes`: registered grexes with seed parent, pollen parent, registrant, originator, registration date, source URL, and verification state.
6. `cultivars` and `cultivar_awards`: clone names, awards, and source evidence.
7. `image_evidence`: only permitted images or private uploads with source URL, license, photographer, rights holder, and access date.
8. `label_ocr_jobs` and `identification_runs`: generated by Edge Functions after uploads.

## Import gates

- Do not import restricted images into public buckets.
- Do not republish registry or award data unless the source license allows it.
- Keep botanically accepted species separate from horticultural grexes and cultivars.
- Mark uncertain parentage, labels, or licenses as `unreviewed` or `doubtful` until curated.
- Treat every identification as probabilistic candidate evidence, not a final determination.

## Local bootstrap

```bash
supabase db reset
# Supabase automatically applies migrations and seed.sql in local development.
```

For a remote project, apply migrations first, then run the seed with a privileged database connection only if these demo rows are useful for staging.

## Validated catalog importer

Production-shaped batches can be expressed as a normalized JSON catalog and checked without writing to a database:

```bash
npm run import:check
node scripts/import-catalog.mjs --dry-run path/to/authorized-catalog.json
```

After the dry run passes, import into a migrated staging project from a trusted server or operator workstation:

```bash
SUPABASE_URL=https://your-project.supabase.co \
SUPABASE_SERVICE_ROLE_KEY=server-only-secret \
node scripts/import-catalog.mjs path/to/authorized-catalog.json
```

The importer writes through Supabase REST in dependency order and upserts deterministic UUID identifiers. It refuses malformed records, incomplete image provenance, invalid parent kinds, and restricted images copied into Storage. Never expose the service-role key in the browser or commit it. `data/catalog.example.json` is a safe manifest template; transform authorized source exports into this normalized shape before import.

## GBIF Orchidaceae synchronization

The GitHub workflow starts automatically when the synchronization/import code is
merged into `main`, as well as monthly or by manual dispatch. It caches every
downloaded GBIF page between runs, publishes the normalized JSON as a build
artifact, and writes the actual genus, accepted-species, and synonym counts to
the workflow summary. A failed or interrupted run can therefore resume instead
of discarding already downloaded pages.

Generate a real taxonomy catalog directly from the public GBIF Species API (accepted species and synonyms only; no occurrence media are downloaded):

```bash
npm run catalog:gbif
node scripts/import-catalog.mjs --dry-run data/generated/gbif-orchidaceae.json
```

Use `--limit 100` for a small staging batch and `--output <path>` to select another destination. The generator paginates API responses, creates deterministic UUIDs, associates synonyms only when their accepted species is present, and records the GBIF endpoint and access date. The resulting snapshot still requires taxonomic review and later reconciliation against WCVP/POWO; it is not a source for registered grexes, cultivars, awards, or images.

Every downloaded API page is checkpointed under `data/generated/gbif-cache`, so rerunning the command resumes an interrupted multi-thousand-record download instead of starting over. Requests retry temporary network and rate-limit failures with exponential backoff. The importer writes catalogs to Supabase in batches of 500 rows to avoid a single oversized REST request.

The GitHub Actions workflow `.github/workflows/sync-gbif.yml` can run the complete download on demand or on its monthly schedule, validates the resulting catalog, and publishes it as a build artifact. Its optional `limit` input supports smaller smoke runs. Generated taxonomy is deliberately not committed automatically: a curator should inspect the artifact and import report before loading staging.

## Query imported records from the frontend

After importing into Supabase, copy `config.example.js` to `config.js` and replace the placeholders with `SUPABASE_URL` and the browser-safe anon/publishable key. `config.js` is ignored by Git. The browser calls `POST /rest/v1/rpc/orchid_search`; public results remain constrained by database RLS. A service-role key must never be used in browser configuration.
